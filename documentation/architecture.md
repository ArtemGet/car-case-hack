# Архитектура решения

Задача №7 «Фалькон Тех» (ЛЦТ 2026): **цифровой признак (эмбеддинг) автомобиля** по кропу,
заданному BBox, для **кросс-камерного сопоставления** в **open-set** режиме, без госномера.
Три целевые задачи: (1) эмбеддинг, (2) ранжирование галереи, (3) режим отказа.

Документ описывает компонентную и функциональную архитектуру и **обоснование выбора
технологий**. Связанные документы: `metrics.md` (метрики/порог), `errors.md` (анализ ошибок),
`sources.md` (внешние источники), `README.md` (запуск).

## 1. Функциональная архитектура

Обязательный минимум в зачёт — **офлайн batch-раннер** `images + csv → 3 файла`. Сервисный
контур (API + UI + векторный поиск) даёт демо-прототип и закрывает требования ТЗ п.6.

```
                         ┌───────────────────────────────────────────────┐
                         │            batch-раннер (ОБЯЗАТЕЛЬНО)          │
  images/*.jpg ─────────▶│ service/infer/run.py                           │
  test_query.csv         │   crop → fusion(DINOv2+SigLIP2) → GPU-preproc →│
  test_gallery.csv       │   per-query k-reciprocal → порог отказа        │
                         │ → submission.csv / embeddings.npy / candidates.csv
                         └───────────────────────────────────────────────┘

  ┌──────────────┐   HTTP/JSON    ┌──────────────────────┐   extract   ┌─────────────────────┐
  │  web (React) │ ─────────────▶ │  api (FastAPI)       │ ──────────▶ │ service.infer      │
  │  upload+bbox │  /api/v1/*     │  service/api/app.py  │             │ backends (ONNX/PT) │
  │  top-N, CAM  │ ◀───────────── │  OpenAPI /docs       │             └─────────────────────┘
  └──────────────┘                │  engine / gallery    │
                                  └───────────┬──────────┘
                                              │ ANN / точный поиск
                                  ┌───────────▼──────────┐
                                  │ vector store         │
                                  │ pgvector / FAISS     │
                                  └──────────────────────┘
```

### Развёртывание (docker-compose)

| Сервис | Роль | Порт |
|---|---|---|
| `infer` | batch-раннер, GPU, офлайн | — (volume `/in`, `/out`) |
| `api` | FastAPI + Swagger, GPU | 8000 |
| `web` | React-статика (nginx, SPA-fallback, прокси `/api`) | 8080 |
| `vectors` | pgvector (PostgreSQL 16) | 5432 |

Рантайм-образ — вторая стадия `Dockerfile`, база **`python:3.12-slim`** (не `nvidia/cuda:*`):
содержит `/opt/venv` (`torch==2.6.0` + `onnxruntime-gpu==1.26.0`), код `/app/{reid,service,tools,configs}`
и `artifacts/` ровно с двумя ONNX (`siglip2_fp16.onnx`, `dinov2_b_fp16.onnx`) + `data_manifest.json`;
**без pip и без сети** при инференсе. Сборка (`docker build`) сеть использует и ставит в builder-стадии
`requirements-runtime.txt` (минимальный runtime, **не** полный train-стек `requirements.txt`).

## 2. Компоненты

| Модуль | Отвечает | Не знает про |
|---|---|---|
| `reid/data` | чтение CSV, aspect-preserving кроп, аугментации без hflip, сплиты | модель, метрики |
| `reid/models` | backbone (DINOv2/ConvNeXt/ResNet), GeM/BNNeck/ArcFace-голова | данные |
| `reid/train` | PK-sampling, цикл обучения, EMA, чекпоинты | формат сдачи |
| `reid/rerank` | per-query k-reciprocal, TTA-слияние (историч., в финале OFF), L2-нормировка | другие query (инвариант) |
| `reid/calibrate` | confidence и порог отказа, запись `candidates.csv` | UI |
| `reid/eval` | обёртка над официальным `evaluate.py` (junk + open-set протокол) | обучение |
| `reid/export` | ONNX fp16 экспорт + валидация top-K / cosine | обучение |
| `service/infer` | 3 файла: `run.py`, `backends.py`, `val_eval.py` | HTTP |
| `service/api` | FastAPI/Swagger: `/search`, `/explain`, `/health`, галерея | формат файлов сдачи |
| `web` | React/TS UI: BBox, top-N, Grad-CAM, экспорт | логика модели |

Поток данных:
- **Обучение**: `train.csv` → кроп-кэш 320px → PK-батчи → DINOv2-B + голова → ArcFace-loss →
  EMA-чекпоинт `best.pt`; оценка на hold-out val официальным скриптом.
- **Инференс**: `images + query/gallery.csv` → по одному кропу (aspect-preserving, частичный
  JPEG-декод `Image.draft`) → эмбеддинг → слияние → ранжирование → 3 файла.

## 3. Обоснование выбора технологий

### 3.1 Почему fusion DINOv2 + SigLIP2 (а не один backbone)

- **DINOv2 ViT-B/14** — self-supervised backbone, обученный на больших неразмеченных данных:
  даёт сильные general-purpose retrieval-признаки и устойчивость к ракурсу/освещению.
  Дообучен на наших данных (`+GeM +BNNeck +ArcFace`, PK-sampling) → **val mAP@10 = 0.4208**
  (upstream DINOv2 без обучения даёт 0.4192; обучение улучшило признак и голову). Слабое место:
  домен (автомобили) и редкие ракурсы.
- **SigLIP2 NaFlex 512d** (`occurra/vehicle_reid_siglip2_naflex_512d`, apache-2.0) — публичный
  vehicle-ReID экстрактор, обученный на VeRi/VERI-Wild-подобных данных. Он **frozen**:
  его доменный признак — комплементарен нашему. Zero-shot на нашем val: **mAP@10 = 0.602**
  (наш обученный DINOv2 = 0.421), после k-reciprocal = 0.6495.
- **Почему fusion, а не только внешняя модель:** их признаки ортогональны (generic-структура
  vs vehicle-домен). Конкатенация `L2(concat[L2(siglip), 0.8·L2(dino)]) → 1024d` поднимает
  mAP@10 с 0.6495 (SigLIP2) до **0.6909** (финальный деплой: ONNX fp16, 224-only,
  TTA OFF), то есть внешний признак не подменяется, а дополняется in-domain. Вес 0.8 подобран
  на val (грид w=0.6…1.5; w=0.8 — оптимум, плато устойчиво к 0.7–0.9).
- **Лицензии/воспроизводимость:** SigLIP2 — apache-2.0, DINOv2 — Apache-2.0; URL + sha256
  зафиксированы (`sources.md`). Внешние веса разрешены ТЗ при однозначном публичном источнике.
- **Бюджет:** два fp16 ONNX (DINOv2-B@224 + SigLIP2) = **344.8 МБ**, latency 17.9 мс,
  FPS 314 — fusion укладывается в перф-бюджет (< 2 ГБ, ≤ 40 мс, ≥ 100 FPS) с запасом
  ~2–3×, поэтому отказ от него не нужен (в отличие от ансамблей большего размера).

### 3.2 Почему GeM + BNNeck + ArcFace

- **GeM-пулинг** (generalized mean, p=3) вместо average/max: мягкая интерполяция между
  `avg` (устойчив, но размывает) и `max` (локален, но шумный) — стандарт для ReID-retrieval.
- **BNNeck** — отдельная BatchNorm между глобальным признаком и классификатором: метрика
  (cosine-retrieval) и классификация (ArcFace) разделены, embedding становится лучше
  калиброван для косинуса, что важно для ранжирования и порога.
- **ArcFace** (additive angular margin, m=0.30) — тянет внутриклассовые признаки к центру
  класса и раздвигает межклассовые по углу. Для **open-set** это критично: граница
  «свой/чужой» становится угловой и переносится на невиданные ID.
- Свип гиперпараметров: margin 0.30/0.35/0.40 и 30/40/60 эпох; лучший — 30 эпох,
  m=0.30 (длинное cosine-расписание и больший margin регрессируют).

### 3.3 Почему aspect-preserving кроп и без horizontal flip

- **Aspect-preserving resize + pad (фон = среднее)** вместо `Resize(224,224)`: растяжение
  кропа искажает пропорции кузова (машина «сплюснута»), теряя геометрические признаки
  (соотношение длина/высота, форма крыши).
- **Без `RandomHorizontalFlip`**: автомобиль **не лево-право симметричен** — положение руля,
  шильдики, выхлоп, фары, надписи. Флип создаёт семантически неверные «примеры» и размывает
  доменный признак. Вместо него: color jitter, blur, random erasing/crop, лёгкие аффинные искажения.
- Кроп-кэш 320px + частичный JPEG-декод (`Image.draft`) сделали обучение GPU-bound (util 29→91 %)
  и ускорили val-extract (39.7 → 3.4 с), не меняя семантику.

### 3.4 Почему k-reciprocal per-query (и почему TTA выключен в финале)

- Q&A организаторов **прямо разрешает** re-ranking внутри top-K одного query относительно
  статической галереи, но запрещает query expansion/трансдукцию по `test_query`.
  k-reciprocal — ровно такой gallery-only re-rank: на DINOv2-этапе +0.0396 mAP@10, на финальном
  fusion-конфиге параметры `k1=8, k2=3, λ=0.5`, расширение пула `pool 200→300` даёт **+0.0036**
  (устойчиво на pool 300/500/750).
- Обязательный **инвариант потоковости** (результат запроса не должен зависеть от других
  запросов) зафиксирован и проверяется `tests/test_rerank_streaming.py` (перестановка/удаление
  других query не меняет ранг; 14 тестов).
- **TTA выключен в финале (деплой, 224-only).** Ранние конфиги применяли query-side мультискейл
  (224 + 280, оба кратны patch=14, без hflip) и давали суммарный прирост, но при честном
  no-cache протоколе деплоя выигрыш не подтвердился, а латентность росла. Итоговый раннер считает
  один вход 224: быстрее (17.9 мс / 314 FPS) и не хуже по баллу отказа. SigLIP2 NaFlex и так
  использует патч-бюджет, а не пиксельный скейл.
- Re-rank не входит в замер latency/throughput по протоколу (замер — только `extract()`), но
  он дешёвый на 750 галерейных объектов (единицы секунд на CPU для полного теста).

### 3.5 Почему ONNX fp16 + GPU-preproc + draft-decode

- Замер организаторов включает **весь цикл `extract()`** (чтение + decode + crop + preprocess +
  forward + postprocess + L2), поэтому узкое место — не только GPU-forward, но и CPU-декод JPEG.
- `PIL.Image.draft(1/N)` декодирует JPEG сразу в уменьшенном масштабе (целочисленный DCT) —
  ~2× ускорение декода при незначительной потере качества, поскольку вход всё равно 224 px.
- **GPU-preproc** (CUDA letterbox / normalize / IOBinding) переносит препроцессинг на GPU и
  убирает лишние синхронизации CPU↔GPU; вместе с CPU-префетчем (4 воркера) это перекрывает
  декод с forward.
- **ONNX Runtime fp16** на CUDA EP: DINOv2-B 164.5 МБ (static 224) + SigLIP2 180.3 МБ — сумма
  **344.8 МБ**, ровно 2 ONNX (< 2 ГБ), cosine-близость к fp32 ≥ 0.99979, top-10 overlap
  0.996/0.998, метрика ранжирования не расходится (ONNX rerank mAP@10 = 0.6899).
- Итог: fusion 17.9 мс / 314 FPS / 16.1 ГБ VRAM — бюджет latency/FPS/2 ГБ пройден с запасом.
- Финальная метрика (деплой, 224-only, TTA OFF) = **0.6909**, порог отказа **0.6970806**
  (F1 0.9702 / TNR 1.0 / балл 0.9792).
- Запас на стенд A5000: оценочно **30–40 % медленнее 4090** на этих ViT-B → ~29–40 мс / 106–157 FPS,
  в бюджете. Числа «4090» — наши dev-замеры; **замеры на стенде A5000 — организаторов**.

### 3.6 Почему pgvector / FAISS

- На тесте галерея 750 объектов, точный косинусный поиск мгновенен. Но задача — кросс-камерный
  поиск в городе (масштабирование до ~10^6 объектов), где нужен **ANN**.
- **FAISS** (HNSW / IVF-PQ) — быстрый in-process ANN, оптимален для batch-поиска и экспериментов
  с recall/latency. **pgvector** — ANN внутри PostgreSQL: хранит эмбеддинги и метаданные
  (image_id, bbox, камера, время) транзакционно, даёт SQL-фильтры и персистентность.
- В прототипе оба варианта взаимозаменяемы: `service/api/gallery.py` инкапсулирует поиск;
  контракт API не зависит от конкретного хранилища. План масштабирования (ANN на ~10^6 объектов)
  описан в презентации решения.

### 3.7 Почему FastAPI + OpenAPI

- Тонкий HTTP-фасад **не дублирует** логику эмбеддинга: он вызывает `service.infer.backends`
  через `service/api/engine.py`, ранжирование — `reid.rerank`, порог — `reid.calibrate`.
  Это снижает риск расхождения между batch-сдачей и демо.
- FastAPI автоматически отдаёт **OpenAPI/Swagger** (`/docs`) и валидирует схемы через Pydantic —
  закрывает требование ТЗ и упрощает интеграцию. Контракт для UI — `web/API.md`.

### 3.8 Почему React + TypeScript + Vite

- UI нужен для демо и интерпретируемости: загрузка кадра, рисование BBox, таблица top-N,
  уверенность/отказ, Grad-CAM. Минимальные зависимости (только `react`/`react-dom`), без UI-китов.
- **Никакой сети в рантайме**: UI обращается только к same-origin `/api` (dev — прокси Vite,
  prod — nginx). Если backend недоступен — явная ошибка, без фейковых результатов.
- Сборка — статические файлы, раздаются nginx; в образе браузерной сети не требуется.

### 3.9 Почему Docker / docker-compose офлайн

- Требование ТЗ: инференс одной командой, **без доступа в интернет в рантайме**, все веса внутри
  образа. Многостадийный `Dockerfile`: builder с сетью (pip) → runtime без pip.
- `docker-compose up` поднимает весь контур (infer/api/web/vectors) — воспроизводимость и
  «инженерное качество» (15 % балла). GPU подключается через `--gpus all` (NVIDIA Container Toolkit).

### 3.10 Почему детерминизм и фиксация версий

- Метрика принимается только при совпадении при повторном прогоне: зафиксированы seed, `cudnn.deterministic`,
  pinned ONNX-потоки. Два полных прогона (val и тест) дают байт-в-байт идентичные три файла.
- Точные пины (без `>=`) в `requirements.txt` (train-стек) / `requirements-runtime.txt`
  (runtime-образ) / `pyproject.toml` — окружение воспроизводимо.

## 4. Инварианты и ограничения

- **Потоковость**: результат `rank(q)` не зависит от других query. Разрешены gallery целиком и
  top-K re-ranking внутри одного query. Нарушение — дисквалификация, поэтому покрыто тестом.
- **Нет утечки меток теста**: `vehicle_id`/`camera_id` используются только для обучения и
  кросс-камерного PK/валидации; на инференс не подаются.
- **Бюджет весов < 2 ГБ**: gate считает только сдаваемый `artifacts/` (**344.8 МБ**, 2 ONNX, PASS).
  Внимание: файлы > 100 МБ не проходят в обычный git — нужен **git-lfs** либо размещение по
  URL+sha256 (см. README §4.3).
- **Ограничение fusion**: два прохода forward (ViT-B + SigLIP2) и 1024-d индекс — это цена
  за mAP. При жёстком latency-бюджете есть быстрые варианты `--variant siglip` (10.5 мс) и
  `--variant dino` (13.2 мс) с ожидаемо меньшим mAP.
